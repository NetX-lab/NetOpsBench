For a single case, follow [Quickstart](/docs/quickstart#run-the-xs-case). The examples below use the same reference agent and expect `OPENAI_API_KEY` in the environment.

## Run a suite

The small-suite example selects three Medium cases and launches three workers. Prepare the scenarios first. Preparation writes topology and scenario assets. Deployment begins when you launch a session.

```bash
netopsbench benchmark prepare --scales medium --seed 42
PYTHONPATH=. python examples/02_run_suite.py --vendor openai
```

For a custom selection, pass scenario paths to `bench.sessions.run_suite(...)`. See the [Python API guide](/docs/build-your-agent/python-api-guide#session-apis) for session options.

## Run a full scale or multiple scales

Each worker runs one case at a time in its own lab. The following command distributes all Medium cases across two labs:

```bash
PYTHONPATH=. python examples/03_run_scale_benchmark.py \
  --scale medium --workers 2 --vendor openai
```

To run several scales, prepare each one and pass a space-separated list to the batch script:

```bash
netopsbench benchmark prepare --scales medium,large
BENCH_VENDOR=openai BENCH_SCALES="medium large" bash scripts/run_all_benchmarks.sh
```

Use `BENCH_WORKERS_LARGE=2` to override the Large worker count. Start Xlarge and Fat-tree with one lab until you have measured [host capacity](/docs/debug-operate/host-setup#check-a-larger-deployment).

## What happens between cases

Each worker starts with a complete healthy Pingmesh baseline. With the default recovery policy it can use that baseline for **10 cases**. Before case 11 it calibrates again. A change to the runtime identity or traffic plan also requires a fresh baseline. Elapsed time alone does not expire it. Every case still collects its own observation window and reads the baseline telemetry again so late samples are included.

After a fault, the worker undoes the change, reads back the affected resources, and verifies network state twice. A retry that eventually succeeds triggers a full calibration. A failed restoration quarantines the worker. The agent's diagnosis timeout is a separate budget. See [State-checked Recovery](/docs/architecture/state-checked-recovery) for the checks and custom-fault behavior.

## Reports and cleanup

Session reports live in `.netopsbench/runs/<run-id>/report.json`. Multi-scale batches also write logs and a summary CSV under `scenario_results/`.

The SDK tears down labs it provisions unless you set `keep_runtime=True`. When attaching to an existing runtime, the caller owns teardown. A retained runtime receives a final health calibration. For inspection and teardown commands, see [Operations](/docs/debug-operate/observability#cleanup).
