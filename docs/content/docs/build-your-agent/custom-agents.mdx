---
title: Custom Troubleshooting Agents
description: Implement the diagnosis contract that NetOpsBench evaluates.
---

An agent is any Python object with a `diagnose(context)` method. NetOpsBench passes a `DiagnosticContext`; the agent returns a structured `DiagnosisResult`; the evaluator compares that result with scenario ground truth.

## Agent contract

```python
from netopsbench.sdk import DiagnosisResult

class MyAgent:
    def diagnose(self, context):
        return DiagnosisResult(
            agent_name="my-agent",
            verdict="fault_detected",
            findings={
                "fault_type": "link_down",
                "location": {"device": "leaf1", "interface": "Ethernet0"},
                "evidence": ["Pingmesh loss is concentrated on paths crossing leaf1."],
            },
            confidence=0.82,
            reasoning="Path symptoms and interface counters point to a leaf1 uplink.",
        )
```

Pass the agent to a session API:

```python
from netopsbench.sdk import NetOpsBench

with NetOpsBench(workspace=".") as bench:
    run = bench.sessions.run_scenario(
        scenario="scenarios/generated/xs/generated_link_down_xs_001.yaml",
        agent=MyAgent(),
    )
    report = run.wait(raise_on_failure=True)
```

## Input: `DiagnosticContext`

| Field | Meaning |
|---|---|
| `scenario_id` | Public case identifier. |
| `topology` | Switches, clients, links, and scale-specific topology metadata. |
| `symptoms` | Pingmesh observations with their window and data-quality metadata. |
| `tools` | Optional runtime or MCP-backed tool access. |
| `metadata` | Runtime metadata such as worker-specific environment values. |

Use `context.tools` to investigate the initial observations. Ground truth and private fault-effect checks stay outside the agent context.

## Output: `DiagnosisResult`

| Field | Requirement |
|---|---|
| `agent_name` | Stable identifier used in reports. |
| `verdict` | One of `fault_detected`, `network_healthy`, or `inconclusive`. |
| `success` | `False` when the agent failed to complete. |
| `findings.fault_type` | Canonical fault label when a fault is detected. |
| `findings.location.device` | Predicted faulty device when applicable. |
| `findings.location.interface` | Predicted faulty interface when applicable. |
| `findings.evidence` | Concise evidence used to support the verdict. |
| `confidence` | Float between 0 and 1. |
| `reasoning` | Short explanation tied to observed evidence. |
| `metadata` | Optional provider, model, tool-call, token, or timing details. |

Return `success=False` when execution fails. A successful `inconclusive` verdict means the agent completed its investigation with insufficient evidence. See [Methodology](/docs/run-benchmarks/methodology#scoring-dimensions) for scoring and the [Python API guide](/docs/build-your-agent/python-api-guide#artifacts) for trace recording.

## Reference agent

The runnable examples use `examples.agents.MinimalDeepAgent` by default. It reads episode observations, queries the [diagnostic tools](/docs/build-your-agent/diagnostic-tools), and returns a structured diagnosis. Select a provider with `--vendor`.

## Native Codex

The bundled `examples.agents.CodexAgent` connects the native Codex CLI to this contract. Install `pip install -e '.[codex]'`, install the native CLI 0.159.2 package with its `codex-code-mode-host` helper, and run `codex login`. Then use `PYTHONPATH=. python examples/01_run_scenario.py --agent codex --scenario scenarios/generated/xs/generated_healthy_network_xs_001.yaml` or wrap `CodexAgent()` with `bench.agents.wrap()`.

Each diagnosis runs in a fresh container with anonymous observations, episode-scoped MCP tools and Python/shell access. The container cannot access the repository, scenario answers, Docker socket or management network directly. Only private authentication persists between cases. Defaults are `gpt-6.1-sol`, effort `xhigh`, 600 seconds and 40 MCP calls; constructor options and recorded runtime artifacts make these settings explicit. See `examples/agents/codex_agent/README.md` for image building, isolation and acceptance commands.

## Native Antigravity

On Linux, install `pip install -e '.[agent]'`, Bubblewrap (`bwrap`), and the [Antigravity CLI](https://antigravity.google/docs/cli/tutorial/). The example was tested with `agy` 1.5.14. Set `GEMINI_API_KEY` in the environment for automated runs. The adapter can also read an existing Antigravity sign-in for local testing. Review [Google's headless usage guidance](https://antigravity.google/docs/faq#can-i-use-antigravity-cli-headless-mode-in-third-party-coding-agents-or-automate-account-switching) before using a personal account in an integration.

```bash
netopsbench benchmark prepare --scales xs
PYTHONPATH=. python examples/01_run_scenario.py --agent antigravity \
  --scenario scenarios/generated/xs/generated_healthy_network_xs_001.yaml
```

The adapter starts a fresh CLI workspace for each case, passes the episode MCP endpoint and diagnosis schema, and records the CLI's token usage. Shell commands and file tools are denied. Bubblewrap isolates the filesystem, while the CLI uses the host network and its HTTP proxy settings. In Python, wrap `examples.agents.AntigravityAgent()` with `bench.agents.wrap()` and optionally choose a model available through your authentication method.
